# Rules the code learned

These rules come from a home-automation service that runs on a [neenv](https://github.com/ploutosservices/neenv)
platform. Each rule was written after a failure, and none of those failures was caught by a test written
beforehand. Each section gives the rule, what broke, and how the code now holds the rule. The platform
underneath is assumed throughout: a manifest per service, values rendered by the platform, a scheduler, alerts
that reach a person. None of this is offered as a cut-down version for setups that lack those parts.

## 1. An application does not know its environment

**Rule.** The code carries no URL, port, path or credential, not even as a fallback. A value the service
needs is declared in its manifest and rendered by the platform. A value that is unset at boot stops the
process, with an error that names the variable.

**What broke.** Fallbacks kept working after the thing they pointed at had moved. The failure then turned up
later, somewhere else, and looked like a different bug. A URL compiled into a browser bundle outlived the
deployment that built it.

**How it holds.** Every read of the environment goes through one helper that raises on absence and names the
manifest entry. A check reports three verdicts, not two: configured and present, configured and absent, and
never configured. "I cannot look" and "it is not there" are fixed by different people.

## 2. A value the scanner cannot see is a value nobody renders

**Rule.** Name every environment variable as a literal, where a scanner reading the source can find it, even
when the code reaches it indirectly.

**What broke.** The manifest was generated by scanning for `os.environ.get("NAME")`. Two reads went through a
constant (`os.environ.get(SITE_ENV)`), so the scanner missed them. Those variables were never declared and
never rendered, and a nightly job failed on two machines every night. CI had been listing those exact
variables under a note saying "declared but not read; not a failure", and the note made a real defect read
as housekeeping.

**How it holds.** An indirect read is paired with a tuple whose only job is to be seen:
`_SCANNER_SEES = (os.environ.get("X"), ...)`. The scanner was deliberately not taught to follow dicts. The
rule is that the code that reads a variable makes it discoverable, and a cleverer scanner would hide
violations of that rule.

## 3. A role set as a side effect of import misses every other entry point

**Rule.** When a process's role decides which credential it uses, every entry point of that role sets the
role explicitly. Each entry point is tested with only its own variables present.

**What broke.** The server module set `READ_ONLY = True` when it was imported. The health check of the same
role was a separate entry point that never imported it, so it read the writing token. While one shared env
file held every token, this worked by accident. Once each entry point received only its own variables, the
check failed in production with a 403.

**How it holds.** Each entry point selects its role itself. A test starts each one with only the variables
its manifest entry declares.

## 4. A write door's contract is its SQL, not its docstring

**Rule.** Before the first write to a store you do not own, read the statement that runs and answer one
question: *what happens to a column I do not send?*

**What broke.** An upsert door's docstring said an update "writes only the discovered columns". The statement
was `SET c = %s` for every discovered column, with values taken by `row.get(c)`. A body carrying one
corrected column wrote NULL over the other five on a live row.

**How it holds.** The caller's correction format now refuses a row write that names a single column, and the
refusal says why. A partial body sent to a whole-row door is a deletion, so the wrong shape is made
impossible rather than left to be remembered.

## 5. A hung request leaves no log line

**Rule.** Log a request while it is still running, not only when it finishes.

**What broke.** The service stopped answering three times. It never crashed and never restarted. Its access
log was written on completion, so a request that never finished wrote nothing, and the log of a hung process
looked exactly like the log of an idle one. Every observation came from outside.

**How it holds.** Middleware writes a warning with the method and path once a request has run for 3 seconds,
and writes the elapsed time when it completes. A hang now leaves a first line with no second one, and that
line names the door. Any long step logs its start and its end, never only its end.

## 6. A cache refreshes behind the caller, not in front of them

**Rule.** Held rows are answered immediately, and the re-read runs on a background thread. Only the very
first read waits, and its time limit is set for a genuinely slow source. Every cache is filled at startup,
when nobody is waiting.

**What broke.** A 300-second TTL made the first caller after expiry pay for the re-read, and every other
caller queued behind them. When the source slowed to about 7 seconds per table, one route took 70 seconds.
The first wrong fix was a tight time limit on the read, which refused reads that were only slow. The second
was warming one of two caches at startup, which left the other cache's first caller timing out at 60 seconds.

**How it holds.** One refresh policy object is shared by every cache. Three separate copies was how the
second cache stayed broken after the first was fixed. A slow refresh logs the table and the seconds it took.

## 7. A check reports its findings; its exit code says only whether it ran

**Rule.** A check's exit code answers "could I run?", never "what did I find?". A finding goes through the
check's verdict output. A check that cannot run names the input it is missing. A comparison that could not
be made is reported as NOT COMPARED with the reason, never skipped in silence and never counted as failures.

**What broke.** A drift check exited 1 when it found drift, so the scheduler reported "the job died" beside
the real finding, with the same timestamp. A register check died at its first missing credential and printed
an interpreter error where a reason belonged. A partial snapshot was compared row by row, so every device
behind one unreachable gateway was reported as a phantom.

**How it holds.** Checks return a list of (subject, verdict, reason) and exit 0 whenever they ran. Whether a
condition warns or fails is argued in the code. A check that is permanently red where red is expected is a
check people stop reading.

## 8. Moving a store means moving what the filesystem did for free

**Rule.** Before replacing files with a database table, list what the files gave you without asking:
independent writers that coexist, isolation per writer, a modification time, a history. Rebuild each one
deliberately, or say that it is gone.

**What broke.** Two sites each committed their own file of router leases. The move put both into one table
behind a door that replaces the whole set. On the first night one site's write marked the other site's rows
as deleted: 100 rows became 60.

**How it holds.** Every writer reads, merges, writes, then reads back, and retries if what it wrote is not
there. It trusts the read-back, never the receipt, because a receipt describes a write that may already
have been replaced. The reader was moved in the same change, so the files and the table could not drift
apart.

## 9. A test checks the property, wherever it lives

**Rule.** A test that guards a property follows that property through refactors. A source search covers
every module the application ships, and a slice of source ends at the next definition, not at the end of
the file.

**What broke.** A vendor client moved into its own module, and three tests failed. Two searched one file for
the wire call. The property was "wherever the wire call lives, its function holds the write gate", not
"the call is in this file". The third counted calls from a function to the end of the file, so it counted
the next function's calls too. A test that encodes a location fails on a refactor and passes on a real
defect that happens to live elsewhere.

**How it holds.** Each test's label states the property it checks, so a test that has drifted from its
property says the wrong thing out loud.

## 10. A probe of a device is load on that device

**Rule.** Before probing a device that production reads, find production's reading interval. Probe at most
once a minute, offset from production's reads, over one session, and stop at the first failure.

**What broke.** A solar gateway was polled every 3 seconds from a development machine, and a new token was
minted for most of the polls. The gateway answered production's collector with 503 for ten minutes straight,
and recovered when the polling stopped. There is no test copy of a house: the device you measure is the one
production depends on.

**How it holds.** Each device's register entry carries a minimum reading interval. One process owns each
device and holds its one session (see [one owner per device reach](one-owner-per-reach.md)).

## 11. A rotating token has one holder

**Rule.** Prove a credential path once, then stop. Never refresh a rotating token anywhere except on the
machine that holds it.

**What broke.** A TV driver was tested from a development machine by refreshing its rotating token. Each
refresh made the copy in production invalid, and recovery took a code change, a re-placement and a fresh
approval in a browser.

**How it holds.** A newly issued rotating token is stored exactly as issued, without a local refresh, so
production is the only holder that ever rotates it. See [one refresh per refused token](one-refresh-then-an-hour.md)
for how often that holder may refresh.

## 12. A declared route answers on every name

**Rule.** If the manifest declares a health route, every name the service answers on serves it with a 200.
A door is checked by a 200 on its declared route, never by the fact that it refuses something.

**What broke.** Two webhook doors answered the health route with 405 and 403, and the service's own check
counted those refusals as green. A door that refuses everything passes such a check, including a door that
is broken.

**How it holds.** One liveness module serves the route on every door. A door that runs as its own user reads
the deployed commit from `.git` files directly, because git refuses to open a repository another user owns.
